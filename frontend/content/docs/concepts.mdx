This page explains how Quorum is structured. If you're looking for an end-to-end
walkthrough with screenshots, see the [Workspace guide](/docs/workspace-guide).
For a stage-by-stage technical reference, see [Pipeline stages](/docs/pipeline-stages).

## Mental model

Quorum's job is to turn an unstructured question into a structured prediction.
Internally, it does that by maintaining four interlocking objects:

1. A **Project** — the unit of work. Contains the brief, uploaded documents,
   and every artifact generated by the pipeline.
2. An **Ontology** — a topic-specific schema of entity types and edge types,
   designed by the LLM for this particular brief.
3. A **Knowledge graph** — concrete entities and relations extracted from the
   brief and any uploaded documents, validated against the ontology.
4. An **Agent pool** — one LLM-backed persona per speaker-capable entity in
   the graph. Each agent has its own system prompt, stance, bias, and
   personality vector.

Once these exist, Quorum runs a **simulation** (a structured debate over
multiple rounds), produces a **consensus** (the swarm position with explicit
dissents), and generates a **report** (a multi-section markdown document).

## The pipeline at a glance

Quorum's seven stages are:

| # | Stage | What it produces | Endpoint |
|---|---|---|---|
| 01 | Ontology generation | Entity + edge type schema | `POST /api/projects/{id}/graph/ontology/generate` |
| 02 | GraphRAG build | Knowledge graph (nodes + edges) | `POST /api/projects/{id}/graph/build` |
| 03 | Environment setup | Agent personas | `POST /api/projects/{id}/env/setup` |
| 04 | Generate config | Time + per-agent activity + platform configs | `POST /api/projects/{id}/simulation/prepare` |
| 05 | Initial activation | Narrative + hot topics + initial posts | (same as stage 04) |
| 06 | Run simulation | Debate transcript + consensus | `POST /api/projects/{id}/simulation/start` |
| 07 | Generate report | Markdown prediction report | `POST /api/projects/{id}/report/generate` |

There is also an **upload** stage (Stage 0) — `POST /api/projects/{id}/upload` —
that lets you attach reality-seed documents before Stage 01 runs. And a
**deep interaction** stage that lets you chat with any individual agent after
the simulation completes:
`POST /api/projects/{id}/agents/{agent_id}/chat`.

Each stage is a discrete API call you can inspect, replay, or skip.

## Project state machine

A project moves through states as the pipeline progresses:

```
created
  └─→ ontology_generated
        └─→ graph_building → graph_completed
              └─→ env_ready
                    └─→ config_ready
                          └─→ simulating → sim_completed
                                └─→ report_ready
```

Any stage can transition the project to `failed`, but the pipeline is
designed to recover gracefully — most failures only block the failing
stage, not the entire run.

## Data model

### Project

The top-level container. Every API call addresses a project by its ID
(`proj_<12 hex chars>`). Projects are persisted to disk so they survive
backend restarts.

Key fields:

- `brief` — the user's question
- `constraints`, `signals` — optional context
- `uploaded_documents` — list of `{filename, text, char_count}`
- `state` — current `ProjectState` enum value
- `events` — append-only log of every status change (drives the system
  dashboard in the UI)
- `ontology`, `graph`, `agents`, `simulation_parameters`,
  `debate_messages`, `consensus`, `report` — outputs of each stage,
  populated as the pipeline progresses

### Ontology

A typed schema with two parts:

- `entity_types` — exactly 10 entries. The first 8 are concrete types
  designed for the brief (e.g. `HistoricalFigure`, `MediaOutlet`,
  `NationState`). The last 2 are always `Person` and `Organization`
  fallbacks for entities that don't fit any concrete type.
- `edge_types` — between 6 and 10 entries in `UPPER_SNAKE_CASE`
  (e.g. `REPORTS_ON`, `AFFILIATED_WITH`, `OPPOSES`).

The LLM is instructed to design the ontology so the downstream graph
builder produces a clean, useful graph.

### Knowledge graph

A flat list of nodes and edges. Each node has:

- `id`, `name`, `type` (one of the ontology entity types)
- `description`, `attributes`, `is_individual`

Each edge has:

- `id`, `source_id`, `target_id`, `type` (one of the ontology edge types)
- `description`, `strength`

The default graph builder is in-process and bounded to roughly 40 nodes /
60 edges per simulation, which keeps each LLM call under the token
budget. The interface is designed to be swapped for a hosted graph
backend without touching anything else.

### Agent profile

One agent per speaker-capable entity. Each profile contains:

- **Identity**: `id`, `user_name` (e.g. `wuhanuniversity_482`), `name`
- **Persona**: `bio` (~200 chars), `persona` (~1500-2000 char structured
  text with `Background`, `Behavior Profile`, `Unique Memory`, and
  `Social Network` sections), `expertise`, `interested_topics`
- **Personality**: `optimism`, `risk_tolerance`, `caution`, `stance`
  (`support` / `oppose` / `neutral`), `bias`
- **Apparent demographics**: `age`, `gender`, `mbti`, `country`,
  `profession`
- **Provenance**: `source_entity_id`, `source_entity_type` — links
  back to the graph node this agent was generated from

### Simulation parameters

The output of Stage 04. Contains:

- `time_config` — total hours, minutes per round, hour-of-day activity
  multipliers
- `agent_configs` — per-agent activity profile (active hours, posts/hour,
  comments/hour, response delay, sentiment bias, influence weight)
- `event_config` — narrative direction, hot topics, initial posts
  (each tagged with the agent that will publish it)
- `feed_config`, `community_config` — recommendation algorithm weights
  for each platform

### Debate messages and consensus

Stage 06 produces a list of `debate_messages`, each with:

- `agent_id`, `agent_name`, `agent_role`, `agent_user_name`
- `round`, `content`, `confidence`, `stance`

After the rounds complete, a moderator LLM call produces the
`consensus`:

- `agreed_position` — the swarm's recommendation
- `agreement_rate`, `confidence_level` — 0-1 scores
- `dissents` — list of `{agent_name, position}` for agents whose final
  stance diverged

### Report

Stage 07 produces a `Report` with:

- `title`, `summary`
- `sections` — list of `{title, content}` markdown sections
- `markdown` — the full rendered report
- `generated_at`

## Architecture overview

```
┌─────────────────────────────────────────────┐
│  Frontend (Next.js 14 + React + d3-force)   │
│  ─ landing  /  workspace  /  docs           │
│  ─ live graph + debate stream + dashboard   │
└──────────────────┬──────────────────────────┘
                   │ REST (JSON + multipart)
┌──────────────────▼──────────────────────────┐
│  Backend (FastAPI + Python 3.11)            │
│  ─ pipeline.router    7-stage endpoints     │
│  ─ pipeline.models    typed dataclasses     │
│  ─ pipeline.*         per-stage services    │
│  ─ llm.py             provider abstraction  │
└──────────────────┬──────────────────────────┘
                   │
   ┌───────────────┼────────────────┐
   ▼               ▼                ▼
 Google         Azure AI        Anthropic
 Gemini         Foundry         Claude
```

The backend has no required external dependencies beyond your chosen
LLM provider. Project state is persisted to a local pickle file
(`backend/.quorum_projects.pkl`) so projects survive backend restarts.

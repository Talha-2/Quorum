## Mental model

Quorum is not a chatbot with extra prompt tricks. It is a project-based
pipeline that accumulates typed artifacts over time, specialized for one
flagship use case — **engineering RFC review**.

The central object is a **Project**. Every stage reads from the project,
writes back to the project, and persists the updated state. That is why the
system is inspectable: you can fetch the project after any stage and see
exactly what has already been produced.

## Domains

A **Domain** specializes the pipeline for one application area. Two domains
ship today:

- **`engineering_rfc`** (default) — the platform's flagship. Pins a fixed
  10-type RFC ontology, a 7-seat reviewer roster (Principal Engineer,
  Reliability, Security, Cost, Product, Tech Lead, Skeptic), and an
  8-section ADR outline. Stages 01, 03, and 07 use the fixed artifacts
  instead of asking the LLM to invent them.
- **`general`** (fallback) — domain-agnostic. The LLM designs the ontology
  and the agent panel from the brief. Use this when the engineering RFC
  reviewer doesn't fit your decision.

Domains are a small extension point — one Python file under
`backend/src/quorum_backend/domains/`. To register a different reviewer
roster for your team, see [Agent architecture](/docs/agent-architecture).

## Core artifacts

### Project

The unit of work. A project contains:

- the decision statement (the "brief")
- optional constraints and signals
- uploaded design docs
- the selected domain
- stage outputs
- event log
- current pipeline state

### Ontology

The schema the pipeline extracts against. For `engineering_rfc` it is a
fixed 10-type schema: `Decision`, `Alternative`, `Tradeoff`, `Constraint`,
`Component`, `ExternalDependency`, `FailureMode`, `NonGoal`, `Stakeholder`,
`Reviewer`. For `general`, the LLM designs one per brief.

The ontology is applied before the graph so extraction happens against an
explicit vocabulary instead of uncontrolled free text.

### Knowledge graph

The graph is the world model for the deliberation. For an RFC review:

- nodes are decisions, alternatives, trade-offs, constraints, components,
  failure modes, and stakeholders extracted from the brief and any
  uploaded design docs
- edges capture relations like `CONSIDERS`, `INVOLVES_TRADEOFF`,
  `CONSTRAINED_BY`, `AFFECTS`, `DEPENDS_ON`, `RISKS`

Every downstream stage depends on the graph being coherent.

### Reviewer profiles

For `engineering_rfc`, the seven reviewers are instantiated deterministically
from the standing roster — same coverage on every RFC. For `general`,
agents are derived from speaker-capable graph entities. Each reviewer or
agent preserves its provenance, so the UI can connect graph view, panel
view, and debate transcript.

### Simulation parameters

Stage 04 generates the behavior envelope for the swarm:

- time configuration
- agent activity profiles
- platform configuration

This stage does **not** generate activation anymore.

### Activation plan

Stage 05 generates the narrative seed for the simulation:

- narrative direction
- hot topics
- starter posts

These starter posts become round `0` transcript entries when the simulation
starts.

### Debate transcript and consensus

Stage 06 produces the running argument:

- debate messages by round
- consensus statement
- dissents

### Report

Stage 07 turns the transcript into a structured Markdown document. For
`engineering_rfc`, the report is an **Architecture Decision Record** with
a fixed eight-section outline (Context, Decision drivers, Alternatives
considered, Recommended decision, Why not the alternatives, Dissents,
Consequences and risks, Follow-ups) plus a provenance footer with a
clear disclaimer that the engineering team owns the final call.

## State machine

The project state progresses through:

```text
created
  -> ontology_generated
  -> graph_building
  -> graph_completed
  -> env_ready
  -> config_ready
  -> activation_ready
  -> simulating
  -> sim_completed
  -> report_ready
```

Any stage can also move the project to `failed`, with the failure reason stored
on the project.

## Why the ordering matters

The order is intentional:

1. ontology constrains the graph
2. graph defines which entities become agents
3. agents define which activity profiles are needed
4. config defines how the simulated environment behaves
5. activation defines what round zero looks like
6. simulation creates the evidence trail
7. report summarizes that evidence trail

If you skip or merge those boundaries carelessly, the artifacts stop matching
the operator mental model and the docs become wrong again.

## Progress visibility

Quorum exposes pipeline progress through `GET /api/projects/{id}/pipeline`.
That endpoint is the canonical stepper status for the workspace and for any
external operator tooling.

## Current system boundary

The runtime path is now intentionally simple:

- one workspace UI
- one project router
- one persisted project model
- one provider abstraction

The older parallel simulation surface and unused frontend workspace branch were
removed to keep the product model coherent.

Quorum convenes a virtual reviewer panel to deliberate on an engineering
proposal. You create a project, attach your design doc, step through a strict
seven-stage pipeline, and finish with a structured **Architecture Decision
Record** (ADR) — recommended decision, alternatives considered, dissents
preserved verbatim, consequences and follow-ups — plus a debate transcript
and post-run chat with any reviewer.

The platform's flagship use case is **engineering RFC review**. A `general`
mode remains for non-engineering deliberation, but every default in the
product — the workspace placeholder, the example brief, the example ADR —
assumes you're reviewing an RFC.

## Flow at a glance

The pipeline is intentionally linear. Each stage has one job, one persisted
output, and one set of prerequisites enforced by the backend.

## What Quorum does

Quorum is built for engineering decisions where the *rejected* alternatives
matter as much as the chosen one. The system:

1. Builds a project from a decision statement and optional design docs.
2. Applies the fixed engineering RFC ontology (Decision, Alternative,
   Tradeoff, Constraint, Component, FailureMode, Stakeholder, Reviewer).
3. Extracts a typed knowledge graph of the decision under review.
4. Convenes the standing seven-seat reviewer panel — Principal Engineer,
   Reliability, Security, Cost, Product, Tech Lead, Skeptic.
5. Generates the deliberation configuration.
6. Generates an activation plan that seeds the debate.
7. Runs a structured multi-round deliberation, capturing dissents verbatim.
8. Emits an eight-section ADR and supports follow-up chat with any reviewer.

The pipeline is intentionally sequential. Each stage validates its
prerequisites, persists its output, and exposes enough intermediate state to
debug a review without guessing.

## Product principles

- **One specialized use case**: engineering RFC review is the default domain;
  the platform leans into it across landing copy, workspace defaults, and the
  reviewer panel.
- **One production path**: the project-based `/api/projects/*` pipeline. The
  earlier legacy simulation surface has been removed.
- **Typed artifacts over ad hoc prompts**: ontology, RFC graph, reviewers,
  config, activation, transcript, consensus, and ADR are all persisted
  project artifacts.
- **Strict stage ordering**: uploads happen before ontology, activation
  happens before deliberation, and ADR generation happens only after a
  completed run.
- **Offline-verifiable**: the local deterministic LLM provider understands
  the production pipeline prompts, so the end-to-end path is testable without
  a vendor API.
- **Documentation in the app**: the Fumadocs site under `/docs` is the
  primary documentation surface and ships with the product.

## Overview

The production pipeline is sequential and project-based. Each stage validates
its prerequisites server-side, persists its output, and exposes the updated
project immediately after completion.

There are seven primary stages after project creation:

1. Ontology generation
2. Graph build
3. Environment setup
4. Simulation config
5. Initial activation
6. Simulation
7. Report generation

There is also:

- **Stage 0**: project creation and optional reality-seed uploads
- **Stage 8**: post-run agent chat

![Quorum pipeline stage flow chart](/docs-images/pipeline-flow.svg)

*Pipeline: the backend enforces this order even if a caller skips around in
the UI or automates through the API. For the engineering RFC domain, stages
01, 03, and 07 use fixed Python constants (no LLM); stages 04 and 05 are
skipped entirely; stage 06 convenes the full panel with a dedicated Skeptic
cross-examination at the end of each round.*

## How to read the flow

The important detail is not just the labels, it is where responsibility sits:

- the frontend exposes the stages one by one
- the backend validates prerequisites again on every mutating request
- `pipeline/run-next` advances exactly one required stage per call
- uploads are intentionally outside the main numbered sequence and close once
  ontology generation begins

## Stage 0: Create project and upload source documents

Endpoints:

- `POST /api/projects`
- `POST /api/projects/{id}/upload`

This stage creates the project shell and optionally attaches source documents.
Uploads are allowed only before ontology generation begins.

Why that restriction exists:

- later stages depend on the source context
- changing inputs mid-pipeline would invalidate downstream artifacts

## Stage 1: Ontology generation

Endpoint:

- `POST /api/projects/{id}/graph/ontology/generate`

This stage asks the LLM to design a topic-specific schema for the brief and any
uploaded material.

Output:

- exactly 10 entity types after normalization
- 6 to 10 edge types after normalization

Robustness measures:

- schema normalization
- required fallback entity types
- parse validation before the project is advanced

## Stage 2: Graph build

Endpoint:

- `POST /api/projects/{id}/graph/build`

This stage extracts concrete nodes and edges using the ontology as the allowed
schema.

Output:

- `graph.nodes`
- `graph.edges`
- `graph_stats`

Robustness measures:

- truncation-aware JSON handling
- repair attempts for incomplete JSON
- type validation against the ontology

## Stage 3: Environment setup

Endpoint:

- `POST /api/projects/{id}/env/setup`

This stage turns speaker-capable graph entities into agents.

Output:

- `agents`
- `agent_count`

Robustness measures:

- speaker-capable filtering before persona generation
- batched persona generation
- fallback personas when a batch fails

## Stage 4: Simulation config

Endpoint:

- `POST /api/projects/{id}/simulation/prepare`

This stage generates the structural behavior configuration for the run.

Output:

- `time_config`
- `agent_configs`
- `feed_config`
- `community_config`

What changed in the production refactor:

- this stage no longer pretends to include activation
- activation was split into its own explicit stage

## Stage 5: Initial activation

Endpoint:

- `POST /api/projects/{id}/simulation/activate`

This stage generates the narrative seed that the simulation actually consumes.

Output:

- `activation.narrative_direction`
- `activation.hot_topics`
- `activation.initial_posts`

The backend assigns starter posts to real agents deterministically. The
simulation runner then injects these posts as round `0` transcript entries.

## Stage 6: Simulation

Endpoint:

- `POST /api/projects/{id}/simulation/start`

The simulation runner uses:

- project brief
- agent personas
- activation context
- transcript-so-far

Output:

- `debate_messages`
- `consensus`

Round zero is seeded from the activation plan. Later rounds build on that
context rather than ignoring it.

## Stage 7: Report generation

Endpoint:

- `POST /api/projects/{id}/report/generate`

The report generator plans a structure first, then writes section bodies using
the transcript and consensus as evidence.

Output:

- report title
- summary
- markdown sections
- full markdown document

## Stage 8: Deep interaction

Endpoint:

- `POST /api/projects/{id}/agents/{agent_id}/chat`

This stage is optional and downstream from the simulation. Agent chat uses the
persona, activation context, transcript summary, and consensus.

## Sequential execution helper

Endpoint:

- `POST /api/projects/{id}/pipeline/run-next`

This helper executes exactly the next incomplete required stage once. It is
useful for automation, CLI wrappers, and tests, while still preserving the
same server-side stage ordering as the UI.

## Operational guarantees

The current pipeline provides these guarantees:

- stage prerequisites are checked server-side
- mutating stages are serialized per project
- completed stages are effectively idempotent
- every successful mutation is persisted
- pipeline status is queryable through `GET /api/projects/{id}/pipeline`
